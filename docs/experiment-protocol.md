# Experiment Protocol

This document defines the evaluation protocol used by RepoDoc. It is not tied to
one experiment; its purpose is to make baselines and our method comparable under
the same inputs, rubrics, judges, and accounting rules.

## 1. Research Questions

- **RQ1 (generation quality)**: On the same repository snapshot, how well do
  generated docs cover the CodeWikiBench rubric? What differs in total score,
  topics, and missed leaves?
- **RQ2 (incremental updates)**: After code moves from base to target, does an
  incremental update preserve quality relative to a full rebuild? Are cost, time,
  and changed pages substantially lower? Are there regressions?
- **RQ3 (ablations)**: How do graph construction, module partitioning, agent
  count, artifact analysis, prompts, and models affect quality and cost?

## 2. Experiment Unit

An experiment unit is:

```text
(system, repository, commit/snapshot, generation config, update mode)
```

- `system`: a baseline in `configs/systems.yaml` or `ours`.
- `repository`: a repository in `configs/repos.yaml`; the commit comes from
  `data/locks/repos.json` or the config `commit`.
- `generation config`: model, provider, key CLI flags, artifact/prose settings,
  agent concurrency/depth, etc. All must be recorded.
- `update mode`: `full` or `update`.

## 3. Data and Splits

- **full**: all 22 CodeWikiBench repositories.
- **core**: the seven repositories used in the CodeWiki paper tables
  (`split: core` in `configs/repos.yaml`), for fast iteration and the main table.
- **pilot**: a single `OpenHands` run, only for wiring and smoke tests, never for
  paper conclusions.

Every repository must be pinned to the commit in benchmark metadata. Do not use
`HEAD` for final results; `prepare --allow-head` is for debugging only.

Do not expand the number of repositories per language at this stage: choose one
medium-sized repository per language for `system × repo` comparisons (Python has
GraphRAG/Rasa). When adding a language, implement the tree-sitter analyzer first,
then run one repository through the same harness.

## 4. Rubric Protocol

The rubric is the test set and must be frozen before running systems.

1. Generate it from benchmark reference docs (`structured_docs.json` +
   `docs_tree.json`).
2. Generate rubric sets with multiple models independently, then semantically
   combine them. Defaults are in `configs/evaluation.yaml`.
3. Use a language-agnostic prompt by default so the rubric does not favor one
   language's implementation details.
4. Manually spot-check hierarchy, leaf decidability, weights, and accidental
   reference-path leakage.
5. Freeze to `data/rubrics/<repo>/combined_rubrics.json` and record SHA-256
   (the harness writes it to `meta.json`).
6. Every system uses the same rubric. Never regenerate or select a rubric for one
   system.

If a rubric is generated by multiple people or rounds, keep per-model JSON and
combine logs.

## 5. Generation Protocol

### 5.1 Full Generation

```bash
# 1) Prepare commit + reference docs + frozen rubric
python -m harness prepare --repo OpenHands --from-hf

# 2) Generate + parse + judge
python -m harness run \
  --system codewiki --repo OpenHands --experiment pilot
```

### 5.1.1 Document Levels and Architecture Pages

Ours uses two documentation levels:

- **leaf / implementation pages**: responsibilities, public APIs, implementation,
  and dependencies;
- **top-level / subsystem / overview pages**: boundaries, component relations,
  runtime and data flows, design decisions, extension points, and tradeoffs,
  expressed with Mermaid diagrams. The overview includes at least one end-to-end
  flowchart and one sequenceDiagram; L2 component pages include at least one
  flowchart.

In addition to rubric coverage, report high-level Mermaid count/syntax errors,
cross-module link integrity, and architecture-topic scores. Do not evaluate docs
only by volume or API coverage.

The harness provides two architecture commands:

```bash
# Export an architecture-focused subset from a frozen rubric
.venv/bin/python -m harness architecture-rubrics \
  --rubrics data/rubrics/<repo>/combined_rubrics.json \
  --out runs/<experiment>/architecture-rubrics.json

# Recompute architecture scores and document metrics from judge results
.venv/bin/python -m harness architecture \
  --results runs/<experiment>/systems/<system>/<repo>/results/combined_results.json \
  --docs runs/<experiment>/systems/<system>/<repo>/docs
```

The architecture subset is not the official CodeWikiBench "Architecture" topic.
The current implementation selects leaves from the frozen rubric using auditable
keywords in `configs/evaluation.yaml`, and can include explicit top-level topics
via `include_topics`; it recomputes weights using the original hierarchy. Reports
must include the filter terms/topics, selected leaf count, total leaf count, and
full-rubric score.

Controls:

- The same repository uses the same commit.
- Within an experiment, rubric, judge model, batch size, and judge prompt/tool
  settings are fixed.
- Record the generation model/version, key flags, and whether README/docs outside
  the reference docs are used.
- For stochastic systems (temperature > 0, random sampling), repeat each
  configuration at least three times with distinct experiment suffixes
  (e.g. `core-r1`, `core-r2`).
- Experiment names use `<language>-<repo>-<scope>-v<N>` and the directory layout
  `runs/<experiment>/systems/<system>/<repo>/`; see `runs/README.md`.

### 5.1.2 Token, Cost, and Time Accounting

Report cost efficiency together with quality, using the same accounting for
CodeWiki and ours:

- `generation.tokens.input/output/reasoning/total`: aggregated from
  `usage.totals` in `metadata.json`;
- `generation.cost_usd` and `cost_status`: provider list cost; mark missing values
  as `partial`/`unknown`/`unavailable`, never average them as zero;
- `generation.duration_sec`: harness end-to-end wall time, including adapter,
  retries, writes, and same-level concurrency;
- `generation.llm_duration_sec`: system-recorded LLM time, `null` when unavailable;
- report per-page tokens, cost, and time as well as totals;
- judge tokens/time go in `judge.tokens` / `judge.duration_sec`;
- incremental updates use `repodoc stats --run-scope latest-run` for that update's
  ledger; do not treat cumulative state usage as one update's cost.

If a CodeWiki demo `metadata.json` has no usage (older version or external
export), report it as unavailable and do not compare its tokens/cost directly
with ours. A formal comparison must rerun CodeWiki locally with the same model
and version and record usage.

### 5.2 Incremental Updates

Recommended runs:

```text
base-full       at base commit     -> docs_base
update-full     at update commit   -> full rebuild docs_full
update-incr     at update commit   -> incremental docs_incr from docs_base
```

Example:

```bash
# Full base commit
python -m harness run --system codewiki --repo svelte --experiment javascript-svelte-base-v1 --ref base

# Set update_commit in repos.yaml/locks and prepare
python -m harness prepare --repo svelte --allow-head   # or set update_commit after --from-hf

# Full update commit
python -m harness run --system codewiki --repo svelte --experiment javascript-svelte-full-v1 --ref update

# Incremental update from base docs
python -m harness update \
  --system codewiki --repo svelte --experiment javascript-svelte-update-v1 --ref update \
  --base-docs runs/javascript-svelte-base-v1/systems/codewiki/svelte/docs
```

Evaluation:

- **End-state quality** (primary): generate a rubric at the update commit and
  judge `docs_full` and `docs_incr` with the same rubric/judge.
- **Retention/regression**: judge `docs_base` and `docs_incr` with the base rubric
  to detect broken requirements; also measure page additions/deletions/changes,
  link integrity, and Mermaid errors.
- **Efficiency**: generation time, tokens, cost, changed page count, and manual
  spot-check time.
- **Staleness**: whether requirements introduced/changed at the update commit are
  covered.

CodeWikiBench has no dedicated automatic update metric. Retention/staleness need
analysis scripts or manual annotation beyond `metrics.json`; do not present them
as the rubric total.

## 6. Judge Protocol

- Use at least one judge different from the generator; three judges are
  recommended for main experiments, combined with `average`.
- Fix judge model, provider, batch size, tools, and retry settings per experiment.
- Judge inputs are the parsed docs tree and rubric only; reference docs must not
  be visible.
- A leaf with `evaluation.error=true` counts as uncovered (score 0) and is
  reported separately. Runs with a high error rate must be rerun.
- Inspect per-leaf std for judge disagreement; report high-variance topics rather
  than only the mean.

Known limitation: CodeWikiBench API judges do not backfill token usage, so judge
cost must be estimated from calls or provider billing.

## 7. Metrics

Primary:

- **Weighted rubric score (0–100)**: binary leaf coverage aggregated bottom-up
  with hierarchy weights.
- **Topic scores**: top-level rubric scores for capability analysis.
- **Coverage/error**: leaf count, missed leaves, evaluation errors.

Efficiency and engineering:

- generation wall clock, judge wall clock, total time;
- generation tokens (input/output/cache), cost when reported;
- docs pages, bytes, words;
- update changed pages, diff size, broken links, Mermaid errors.

Statistics:

- Report scores per `(system, repo)`; the main table reports system mean/min/max.
- Repeat stochastic methods at least three times and report mean ± std; paired
  comparisons within a repository are preferred over global means.
- Do not hide per-repo failures behind averages; `summary.md` and `batch.json`
  retain failures.

## 9. Validity Threats

- **Judge bias**: LLM judges may prefer longer or more familiar structures. Use
  multiple judges, spot checks, and per-topic analysis.
- **Rubric quality**: rubrics derive from reference docs and may miss behavior
  absent from them; this is a benchmark limitation.
- **Data leakage**: generators can read repository README/docs. Record
  `--with-prose` usage because it may expose reference content.
- **Model drift**: record model name, provider, and date; API models can change.
- **Cost accounting**: providers differ in pricing, cache, and subscriptions.
  Compare costs within a provider and also report tokens and calls.
- **Update commit choice**: diff size strongly affects update gains. Use multiple
  commits with different sizes/types, not only the most favorable one.
